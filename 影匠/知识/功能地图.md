## 0. 一句话结论

飞彩工作台 = **一条「剧本 → 分镜 → 生图 → 生视频 → 配音 → 成片」的本地流水线**，外面套了四样影匠现在完全没有的东西：

1. **模型接入层**（模型注册表 + 中转协议 + 插件 SDK）——把几十家模型服务抽象成同一套 HTTP 契约，这是最值得抄的部分；
2. **无限画布**（`app/comfyui/canvas/` 206 个文件）——把整条流水线变成可拖拽的节点图，节点即功能；
3. **持久任务账本**（任务落盘 + 幂等 + 禁止自动重试的「终态未知」判定）——花钱的操作绝不重复扣费；
4. **可用性/资产面板**（左侧一致性面板、`/library`、`/model-monitor`）——把上面三样变成人能看的东西。

影匠目前的情况（**两轮实测，含本轮新增模块**）：
- **手艺已经超过飞彩**：分镜四阶段（节拍/九宫格/四宫格/动态）、`审片.py` 的硬规则检查、`风格库.py` 23 风格、`角色库.py` 四层一致性锁的中文词典与兜底报警；
- **AI 交互设计与飞彩同水准**：`影匠MCP.py` 独立做出了「统一错误信封 + `可重试` 刹车 + `下一步` 导航」，与飞彩的「终态未知禁止重试」和 `nextActions` 同构，**某些地方比飞彩更早成型**；
- **工程基础设施几乎为零**：没有任务账本、没有模型接入层、没有任务队列、没有可用性面板。**这三样是影匠与飞彩之间真正的差距。**

## 3. 数据持久化设计（反推）

### 3.1 IndexedDB —— 8 个库（实证，全部逐字）

| 数据库名 | 用途（推断依据） |
|---|---|
| `feicai-kv-store` | 通用键值（出现 3 次，含 `model-instance-authority-v1` 权威副本） |
| `feicai-image-store` | 图片二进制本体（对应 `lib/imageDB.ts`，1 处实证） |
| `feicai-script-store` | 剧本（对应 `lib/scriptDB.ts`，1 处实证） |
| `feicai-dubbing` | 配音工程（音频 + 绑定 + 字幕） |
| `feicai-rh-task-queue` | RunningHub 任务队列（**独立队列**，说明它不是内存队列） |
| `feicai-canvas-media-outbox` | 画布媒体出站箱（**outbox 模式**：先落本地，再异步同步） |

| `feicai-novel-workshop-draft-import-journal` | 草稿导入日志（**journal 模式**：可重放） |

**设计要点（三条，最值得抄）**：
1. **outbox / journal / pending 三种持久化原语**：任何「会花钱」或「会丢」的跨进程动作，先写一张日志记录再发请求；失败了能重放，成功了能对账。
2. **大二进制与元数据分离**：`image-store` / `script-store` 只放本体，元数据走 localStorage（key 小、可同步、易调试）。
3. **权威副本 + 本地缓存双层**：`feicai-model-instance-authority-v1`（服务端权威）+ `feicai-model-registry-cache`（本地缓存）+ `feicai-model-instances-revision`（版本号做 CAS）。文案「拒绝降级托管实例修订」（实证）就是这个机制在生效。

## 4. 任务队列与并发（反推）

### 4.1 实测常数与文案（全部实证）

```
maxConcurrent = 1        （2 处）
maxConcurrent = 3        （1 处）
Concurrency = 3          （2 处）
concurrency = 1          （2 处）
```
> 同仓库同时存在 1 和 3。合理解释：**付费/写操作串行为 1，只读/查询类并发为 3**。文案进一步佐证：

> 「本次确定新增 LLM 调用 N 次，**执行并发上限为 3**；**账本查询与任务续查不会新调用模型**。」
> 「各合集的脚本、参考图和失败重试互不影响。」（实证逐字）

### 4.2 队列分层（四层，全部有实证）

| 层 | 载体 | 实证 |
|---|---|---|
| L1 内存队列 | `taskQueue`（3 处） | 函数名 |
| L2 持久队列 | IndexedDB `feicai-rh-task-queue` | 数据库名 |
| L3 **业务账本** | `feicai-library-batch-task-ledger-v1` / `-tasks-v1` / `-image-intents-v1`；`lib/libraryBatchTaskLedger`（推测名） | key 名 ×3 |
| L4 服务端操作 | `/api/video-operations/v2/*`（submissions / result / cancellations / reconciliations / recoveries） | 5 条 route |

**L1→L4 是全链路的**：内存队列丢了不影响 L2，L2 丢了能靠 L3 账本重建，服务端超时能靠 L4 的 `reconciliations` 对账。

### 4.3 重试策略（这套是本仓库最精妙的地方）

**核心判据：区分「确定失败」和「终态未知」。**

| 情形 | 行为 | 实证文案（逐字） |
|---|---|---|
| 参数错误 / 明确的 4xx | **不重试**，不发请求 | 「本次没有发出任何请求，不会产生费用」 |
| 明确失败（上游 200 带错误体 / 明确 5xx） | 可重试（27 处「自动重试」） | 「`${r}${t}`。该次请求结果或计费状态可能无法确认，已停止自动重试，请手动重试」 |
| **终态未知**（超时 / 网络断 / 响应非法 JSON） | **绝不自动重试**，抛 `indeterminate` 错误 | 「LLM 请求可能已经到达供应商，但结果或计费状态无法确认。已停止自动重试，请人工核对后再手动操作。」（`class d extends Error`，带 `this.indeterminate = true; this.chargedUnknown = true`） |
| 校验失败 | 不重试 | 「LLM 已返回结果但未通过本地校验（类别=…）。该次请求可能已计费，已停止自动重试，请人工检查后再手动操作。」 |
| 实例级失败 | 换实例 | 「实例「X」(${model}) 终态未知：${lastError}。**本次未自动重试，请手动更换模型后再试**」 |
| 旧版断点 | 悬空标记，**不迁移不重试** | 「检测到旧版自动化断点（schema N），已标记为悬空；不能静默迁移或自动重试，请核对项目后重新启动」 |

### 4.4 幂等与租约

- **operationId**：「这张资料图有旧版未确认派发记录，已禁止自动重试」「上一次派发状态无法确认，已禁止自动重试」（实证）——同一 operationId 二次派发被硬拦。
- **Key 池**（`[RhKeyPool]`，实测类名与日志格式）：
  - `[RhKeyPool] 已更新: ${n} 个 key, 单 key 并发上限 ${limit}`
  - `slot ${i+1} 超过安全租约仍未 release，强制回收`
  - `当前 RunningHub 付费操作已持有 Key 槽；禁止重复取得创建租约`
  - `当前 RunningHub 付费操作已使用过 Key 槽；禁止重复…`
  - **三层防护**：持有即占槽 → 用过即退休（`retiredOwnedKeys`）→ 超时强制回收（`safetyTimeoutMs`）。
- **权威租约（auto-lock）**：一轮完整的 transport 校验 —— `权威租约返回无效 JSON` / `权威租约响应结构无效` / `权威租约 mutation 响应结构无效` / `权威租约 mutation 响应校验失败` / `更新权威租约超时，请稍后重试`。本地租约缓存失败只 `console.warn`，不阻塞主流程。

### 4.5 停靠点：`video-operations/v2` 的状态机

从 route 名可完整推出一次视频生成的生命周期（实证，逐字）：

### 4.6 对影匠的启示（这是 P0 里的 P0）

影匠 `引擎.派工()` 现在是「提交 → 轮询 → 等 1800 秒 → 拿图」，**没有 operationId、没有账本、没有终态区分**。风险很低（本机 ComfyUI 不花钱），但一旦接云端模型立刻致命。**最小可抄版本**：

```
任务 = { operationId, 命令, 对象, 实例, 提交时间, 状态: queued|running|done|failed|unknown,
         上游任务号, 结果路径 }
终态未知 => 状态 unknown，禁止自动重试，写进账本等人工确认
```

### 5.1 插件 SDK —— 逐字契约（**真实源码**，`Win/docs/model-plugin-example/echo-image/`）

**`plugin.json`（19 行，全文）**：

{
  "id": "echo-image",

  "allowedHosts": ["api.example.com"],

**`adapter.js` 的核心设计原则（原文逐字，这是全仓库最值得抄的一段注释）**：

> 适配器是「纯函数」:不发网络请求、不读密钥、不碰文件系统。
> 它只做两件事:
>   ① 把宿主给的归一化请求 → 拼成 HTTP 意图(方法 + 相对路径 + body)
>   ② 把宿主拿回的上游响应 JSON → 解析成归一化结果
> 其余一切(拼实例 baseUrl、注入鉴权、发请求、b64 落盘换短链)由宿主执行。
> 注意:path 只能是 "/" 开头的相对路径 —— **你物理上无法把请求打到别的域**。
>
> 同步协议:提交一次、响应里直接带图,所以只需要 buildCreate + parseCreate,
> 不实现 buildPoll / parsePoll(异步轮询协议才需要,且**两者必须成对实现**)。
>
> 注册方式(唯一):执行结束时把适配器对象赋给 `globalThis.adapter`。

**适配器接口（逐字）**：

```js
globalThis.adapter = {
  kind: "image",               // 与 plugin.json 里模型的 kind 一致
  family: "plugin:echo-image", // 固定为 "plugin:" + 插件 id
  sdk: 1,
  buildCreate: function (req) { return { method, path, body }; },
  parseCreate: function (raw) { return { status: "done"|"failed", imageUrls?, imageB64?, error? }; }
};
```

**归一化请求 `req` 的字段（实证，从示例代码读出）**：`req.model`（宿主已剥掉 `plugin:<id>/` 前缀）、`req.prompt`、`req.aspectRatio`（如 `"16:9"`，适配器自己转像素）、`req.imageUrls[]`（**可能是公网 URL 也可能是 `data:` URL，上游得两种都认**）、`req.n`（契约里有，当前宿主不填，预留）。

**归一化结果字段**：`status`、`imageUrls[]`（公网 URL）、`imageB64[]`（纯 base64，不带 `data:` 前缀，**宿主负责落盘换短链**）、`error`。

**四道安全闸门（全部在 `plugin.json` 里声明、由宿主强制）**：
1. `allowedHosts` —— 域名白名单；
2. `path` 必须以 `/` 开头 —— 物理上打不到别的域；
3. `auth.type` —— 密钥由宿主注入，适配器读不到；
4. `requiredSdk` —— 版本门。

另有 `echo-video` 示例（3409 B `adapter.js` + 724 B `plugin.json`），结构同构，说明**图像和视频共用一套 SDK**。

### 5.6 影匠该怎么抄（具体到文件）

影匠现在**没有接入层**，`引擎.文生图` 里硬编码了「读模板 → 填节点 → 提交 → 轮询 → 下载」。建议照飞彩的 SDK 做一个 `影匠/接口/` 目录，**先不写插件系统，只把「适配器纯函数」这一条原则落进去**：

```
影匠/接口/
├─ 契约.py        定义 归一化请求 / 归一化结果 两个 dataclass
├─ 本地ComfyUI.py  现有 引擎.py 改造为 adapter：拼工作流 + 解响应
├─ 火山方舟.py     云 GPU / 云端 Seedance（可选）
└─ 注册表.py       {模型ID: (adapter, 能力, 渠道)}
```

**必须照抄的三条**：
1. **适配器是纯函数** —— 不发网络请求、不读密钥、不碰文件系统，只做「归一化请求 → HTTP 意图」和「上游响应 → 归一化结果」；
2. **`path` 只能是相对路径** —— 物理上打不到别的域；
3. **同步协议只要 `buildCreate`/`parseCreate`，异步协议 `buildPoll`/`parsePoll` 必须成对** —— 不允许出现「能提交不能轮询」的半成品适配器。

### 三句话总结差距（复测后）

1. **最大的差距是「持久任务账本」** —— 飞彩所有上层能力（并发 3、恢复、对账、成本预告、operationId 幂等）都长在一本落盘的账本上。影匠已经知道「什么该刹车」（`影匠MCP.可重试`），**但刹完车没地方记账**，进程一退线索就没了。这是唯一一个「不做就永远卡住」的缺口。
2. **第二大是「模型接入层」** —— 飞彩靠「适配器是纯函数 + `path` 只能相对路径 + 同步/异步成对」这条原则，让加模型变成写一个 40 行的 `adapter.js`；影匠的模型逻辑焊死在 `引擎.py` 里，加一个引擎要改核心代码。
3. **第三大是「算出来的东西没有出口」** —— `一致性.py` 能算出参考图数组顺序、`@N` 编号、注入文本、服装推荐，`影匠MCP.py` 能把整条流水线暴露给 AI，但**两者都没有接到 `引擎.文生图` 的参考图参数上**，也没有一个面板能让人看见。影匠不缺「想清楚了」，缺「接通了」。
