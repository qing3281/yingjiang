## 1. 一致性管理的 UI 骨架（先看清它长什么样）

## 2. ★核心问题：参考图到底怎么拼进提示词

### 2.1 答案：三件套，不是「VLM 描述成文字」

飞彩的做法是这三层同时生效：

```
┌─ 第 1 层：图片本体 ───────────────────────────────────────────┐
│  选中的参考图按固定顺序打包成多模态图片数组，随生图请求一起发   │
│  顺序 = 垫图/尾帧 → 角色 → 场景 → 道具 → 其他 → 风格参考图      │
└──────────────────────────────────────────────────────────────┘
┌─ 第 2 层：提示词里的位置编号 ─────────────────────────────────┐
│  提示词正文写 "…@1 站在 @2 中央…"                             │
│  @N 是**位置占位符**，N 由代码按顺序自动分配，人不能自己写死     │
└──────────────────────────────────────────────────────────────┘
┌─ 第 3 层：外置对应表（运行时拼的一段文本）────────────────────┐
│  模板变量 {{reference_block}}                                 │
│  = "参考图1是【角色：叶云】；参考图2是【场景：破庙】；…"        │
│  未选任何参考图时，这个变量为空串                               │
└──────────────────────────────────────────────────────────────┘
```

**为什么必须有第 3 层？** 因为图像模型看不到 `@N` 与图片的对应关系——它只看到「一串图 + 一段文字」。第 3 层就是那根「把编号钉到图上」的钉子。飞彩还额外做了一件事：**把标签文字烧进图片像素**（见 §2.4）。

### 2.2 铁证：提示词编译器的约束原文

`prompt-compiler` 的变量字典里有一条：

```
reference_block = "飞彩运行时组装的参考图编号与语义说明；不需要参考图时为空。"
```

配套的硬约束原文：

> **不得写死 @1、@2 等参考图编号。需要输出参考图说明时，只能放置 `{{reference_block}}`。**

还有一条针对「LLM 改写提示词」的保护：

> 生成提示词时必须**严格保留 `@数字` 占位符**，不得改写或翻译；多模态补充时可以用参考图理解占位符指代什么，但输出仍要保留占位符本身。

这三句话把机制锁死了：
- `@N` 是**约定 syntax**，不是普通文本
- 编号由**运行时**决定，因为参考图选择是运行时行为
- LLM 只被允许**理解**编号，不允许**重写**编号

### 2.3 编号是怎么分配的

打包名 `g1(e, t)` 的函数负责拼编号行（从字符串常量还原）：

```js
// e = 参考图数组（每项有 类型 / 名字 / 英文名 / url）
// t = 模式（决定「参考图」这个中文词还是别的说法）
编号行 = e.map((x, i) => {
  序号 = i + 1
  if (x.类型 === "style")        return `参考图${序号}是【风格参考】`
  if (x.类型 === "costume")      return `参考图${序号}是【服装：${x.名字}】`
  return `参考图${序号}是【${类别中文}：${x.名字}（${x.英文名}）${
      x.类型 === "character" ? "，用于保持画面连续性" : ""
  }】`
}).join("；")
```

关键设计点：

1. **英文名跟着中文名一起给**（`叶云（Ye Yun）`）。图像模型对英文名的锚定更稳，中文名只是给人看的。这解释了为什么影匠必须有一层「中文→英文」的翻译机制。
2. **`用于保持画面连续性` 只加在角色上**，场景/道具不加。这是一条明确的语义提示：角色要跨格长得一样，场景只要风格对得上。
3. **风格参考图单独成类**，不参与角色/场景/道具的三分类。

### 2.4 图片本体是「带烧入标签的合成页」

changelog / 调试报告里有一句原文：

> 以下为实际发送给图像模型的合成参考图（composite sheet）。**角色/场景/道具名已烧入图片像素。**

并且按 `[i/总数] 名称1 · 名称2` 的格式列出每一张 sheet。

也就是说：多张参考图**可能被合成到一张 sheet 上**，每张 sheet 上方用**画上去的文字**标注里面是谁。这样做的好处是**不依赖模型去数图**——模型看到的是「一张图的左上角写着『叶云』」，对应关系是视觉的、不是推理出来的。

**这条对影匠极其重要**：如果影匠不做烧字，就必须靠 §2.1 的第 3 层文字表；两样至少要有一件，最好都有。

### 2.5 每张图的角色说明（注入用的英文模板）

`image-prompt-constraints` 里按类型给图像模型的指令（`image-to-image` 场景），要点还原：

- 通用：`Use the reference images as the primary subject.` + 「注意环境的空间布局、角色与物体在空间中的相对位置」+「生成不同角度的连贯画面以贴合剧情推进」+`Maintain strict consistency with the art style of the reference images.`
- 角色：保持**面部特征、发型、服装、身体比例**一致
- 场景：匹配**环境、光照、氛围**
- 道具：**精确复现**设计
- 图片顺序硬编码为 `{Character: 0, Scene: 1, Prop: 2, Other: 3}`，风格参考图排在最后

### 2.6 生图时的零文字铁律

同一处约束里有一条：

> 成图里不得出现任何文字 —— 台词、对话气泡、字幕、时间码、镜号、水印、角色名、拟声词，一个都不许有。分镜描述里**引号内的台词只作表演提示**（表情、手势、情绪），绝不允许画成可见文字。

以及一条场景类参考图的警告原文：

> **风景参考图不要出现人物正脸，否则破坏一致性！！**

（两个感叹号是原文。）含义：场景参考图里混进人脸，会让模型把那张脸当成角色锚点，从而串戏。

### 2.7 中文描述的用途：只用来「造参考图」，不用来「生分镜」

i18n 键里有一条 `translate_ref_prompt: "翻译参考描述"`（菜单项 `open_ref_bind: "参考图绑定"`、`delete_consistency_item`、`toggle_style_ref: "风格参考图"`）。

用途链路：

```
一致性条目.description（中文，人写的）
   → 「翻译参考描述」
   → 英文 Design Reference Sheet 提示词
   → 生成「角色/场景/道具设定图」（参考图本身）
   → 该图进入角色库，成为 referenceImage
   → 后续每格生图时，这张图**以图片身份**参与，description 不再进提示词
```

**这就是答案的关键分水岭**：中文描述**不会**逐格拼进生图提示词。它是一次性的、用来生产「参考图」这个资产的输入。生图时进提示词的只有 §2.1 的第 3 层（编号 + 实体名 + 英文名）。

影匠的 `一致性.py` 照这个思路实现：`注入()` 里对每条素材给出的英文，来自 `描述 → 译描述()` 的一次翻译，产物是**一条素材的一句话英文身份说明**（喂给模型做锚定），而不是把整段中文描述逐字塞进提示词。

### 2.8 跨格复用：继承链

每格的 `bindIds` 解析顺序（从 entity-match 的字段名还原）：

```
格级 bindIds（最高优先）
  ↓ 没有
组级（四宫格的四格为一组：`四宫格组N参考图`）
  ↓ 没有
全局（九宫格/智能分镜/自定义宫格 的 *-global）
  ↓ 都没有
不挂参考图（合法状态，不报错）
```

字段 `canRestoreInheritance` + `originalBindIds` 的存在说明：**人工改过绑定之后，可以回退到继承来的那一份**。原值被保存下来，不是丢掉。

## 3. 一致性数据模型

### 3.1 实体条目（一份素材）

三个类别，英文键固定：

```
characters  → 角色
scenes      → 场景
props       → 道具
（style 是第四类，但它是「风格参考图」不是实体）
```

通用字段：

| 字段 | 含义 |
|---|---|
| `id` | 稳定 ID（跨会话不变，绑定存的是这个） |
| `name` | 中文名 |
| `description` | 中文描述（人写，用来生成参考图） |
| `prompt` | 英文提示词（翻译产物） |
| `aliases[]` | 别名数组（匹配用） |
| `referenceImage` | 参考图（UI 文案：「已有参考图（将替换）」/「暂无参考图」） |
| `referenceImages[]` | 多张参考图 |
| `category` | `characters` / `scenes` / `props` |

角色特有：**身份锚定（identity anchor）** 指向该角色的**定妆图**（character sheet），对应「角色审美」预设。UI 原文：

> 「AI 提取角色参考图时，系统注入给 LLM 的审美规则。默认东亚。」「用于后续角色提取与参考图生成」

取值 label：`东亚审美 / 日韩系 / 欧美 / 多元混合 / 不限制`（值 id 含 `asian`）。

### 3.2 匹配元数据（entity-match 契约）

`app\api\entity-match` 的字段名原样：

| 字段 | 含义 |
|---|---|
| `mention` | 文本里提到的名字（从剧本/分镜里抽出来的） |
| `candidates[]` | 候选实体列表 |
| `selectedId` | 人工选中的稳定 ID |
| `autoCandidateId` | 系统自动选的候选 |
| `status` | `none` / `review` / `high` —— **待定 / 需人工确认 / 高置信** |
| `confidence` | 置信度 |
| `matchReason` | 匹配理由（可解释性） |
| `intent` | 匹配意图 |
| `canRestoreInheritance` | 能否回退到继承绑定 |
| `originalBindIds` | 继承来的原始绑定（回退用） |

对应 UI 文案原文：

- `"角色库实体已存在，但当前没有可用参考图"` → status `none`
- `"存在多个候选，需人工确认"` → status `review`
- `"已人工选择角色库稳定 ID"` → 已 `selectedId`

**设计要点**：`matchReason` / `confidence` 一起返回，等于让**人**能审。飞彩还配了一个独立的审核面板（`StudioReferenceMatchReview`），支持三种决定：

| 决定 | 后果（原文） |
|---|---|
| `queue-library` | 「确认保存后会加入当前项目角色库**待补区**，不会自动生图」 |
| `ignore-reference` | 「确认保存后会记住本次分镜的『**无需参考图**』决定」 |
| 恢复继承 | 回到 `originalBindIds` |

审核面板的定位原文（很重要，是它的哲学）：

> **审核专员只负责核对本场出场实体。缺失/待确认将不带参考图继续，不会阻塞确认与后续创作。**

—— 也就是**一致性缺失不阻塞流程**。这是影匠该学的：宁可少挂参考图把片子先出来，不要卡在「必须凑齐」。

### 3.3 错误码（绑定面板）

| 码 | 文案 |
|---|---|
| `ENTITY_UNAVAILABLE` | 「该实体还没有参考图，暂时不能选入绑定」 |
| `SELECTION_LIMIT` | `` `每格最多选择 ${n} 张参考图` `` |
| `CELL_NOT_FOUND` | 「分镜已变化，请关闭后重新审核」 |

`ENTITY_UNAVAILABLE` 说明：**没有参考图的实体不能绑**（不能只靠名字占位）。`CELL_NOT_FOUND` 说明绑定是按 `cellKey` 存的，分镜一改 key 就失效 —— 所以影匠的绑定要**按格子 key 存，并在分镜变更后做失效检测**。

### 3.4 溶图合成（创建新实体的一条路径）

UI 原文：「**跨角色/场景/道具选择参考图，合成为新条目**」，「选择 2~9 张参考图（已选 n/9）」。

这是把多张参考图**合成一张新素材的参考图**的功能（比如「叶云 + 破庙」合成一张「叶云在破庙」的环境定妆图）。上限 9 张。影匠对应实现见 `一致性.py` 的 `绑定目录()` + 多图条目。

### 3.5 项目级 + 磁盘持久化

- 角色库是**项目级**的（绑定面板入参带 `currentProjectId` / `currentProjectName`）
- 落盘：`outputs/grid-images/`（按格 key 命名，刷新自动恢复）；参考图另有 `app\api\ref-image\[key]` + `app\api\reference-bundle` 两个路由
- 保存时有**写盘互斥**提示：「当前分镜参考图正在保存…」

## 4. 服装 / 场景匹配（`wardrobeOutfits` / `wardrobeSceneMatch` / `costumePresets`）

### 4.1 诚实说明：核心算法未挖到

`wardrobe` 在**全部 409 个 .js 里只命中 2 个文件、共 4 次**（`app\library\page-37500cd19e450e36.js` 2 次、`8703-eb0f8154d00e5112.js` 2 次）。结合 `Win\app\` 里存在 `app\lib\wardrobeOutfits.ts` 这个 12 字节空壳文件的事实，可以判定：

> **`wardrobeOutfits.ts` / `wardrobeSceneMatch.ts` / `costumePresets.ts` 是服务端模块（或在服务端才被引用的模块），没有被打进客户端 `.next` 打包产物。**

因此：**匹配算法的具体实现（打分公式、关键词表、是否用向量、是否调模型）未挖到。**

### 4.2 从旁证能推出的部分

1. **有独立的换装设计接口**：路由空壳 `Win\app\api\costume-design\` 存在 —— 说明「服装设计/换装」是一等公民，不是角色描述的附属字段。
2. **`costumePresets` 是预设集**：名字里的 `Presets` 说明是「一套预先做好的服装方案」，用户可挑，而非从零写。
3. **服装与角色是「母-子」关系**：一个角色的多套造型共用同一个母角色（这样才能保证「同一张脸换衣服」），因此影匠的数据模型里给 `服装` 加了 `关联角色` 字段。
4. **场景匹配的输入是「本场戏的场景 + 出场角色」**：从一致性管理的整体结构反推（审核按「本场出场实体」走），匹配粒度是**场（beat/scene）**，不是格。

### 4.3 影匠的做法（原创，明确标注是影匠自己的选择）

因为算法未挖到，影匠的 `服装推荐()` 用的是**纯标签重叠打分**，并把公式写在代码注释里，方便以后替换：

```
得分 = 重叠标签数 × 2
     + (服装的 关联角色 命中时 +3)
     + (该服装有参考图时 +1)
```

排序取前 N。`场景标签()` 用**中文 2~4 字滑窗 + 标点切段**从场景描述里抽标签。

**这是权宜之计，不是还原飞彩。** 影匠以后如果拿到更好的做法，直接换掉 `服装推荐()` 即可，接口不变。

## 5. 超分（顺带挖到，与一致性共用同一套参考图机制）

**不是本地 RealESRGAN，而是「把原图当参考图 + 超分提示词」再喂给同一个图像模型。**

- 触发文案：`超分放大 ${cellKey}`，任务类型 `image`
- 目标尺寸：`"4K"→4096`、`"2K"→2048`、其它→`1024`
- 提示词优先读系统提示词库的 `upscale` 项，长度 > 10 才用；否则内置兜底，要点：
  - `Super-resolution task: Reproduce this reference image at ${res} resolution (${px}px long edge).`
  - `CRITICAL — This is NOT image regeneration. Do NOT redraw or reimagine the scene.`
  - `Output a PIXEL-PERFECT copy of the input, only at higher resolution with enhanced sharpness`
  - `Preserve EXACTLY: composition, colors, lighting, shadows, style, every character, pose, expression`
  - 增强优先级：`1. EDGES & LINES`（最高）→ `2. FINE DETAILS`（发丝/织物/皮肤微纹理/睫毛/虹膜）→ `3. FACIAL CLARITY` → `4. ARTIFACT REMOVAL`（去压缩块/色带/振铃）→ `5. TEXTURE FIDELITY`
- 超分前先读源图宽高并打日志：`[upscaleCell] source: ${w}×${h}, target: ${res} (${px}px)`
- 同格互斥：正在超分中 → 「该格正在超分中」

**对影匠的启示**：做超分不要装 RealESRGAN，走「原图 + 超分提示词 → 图像模型」这条路，关键是「不是重画」和「像素级复制」这两句话必须写进去。

### 6.5 中文→英文翻译机制（复用 `角色库.py`，只读）

- `角色库.py` 有 96 词对照词典 `_词典` + `_译(词, 报)` 函数（实测载入后词表 99 条）
- `_译` 的行为：整串命中 → 按 `[，,、;；/|·]+` 切段 → 段内最长词优先替换 → **还有汉字就报警并丢掉**
- `一致性.py` 的 `译描述()` **直接复用 `_译()`**，并把它的报警接成返回的「未命中」列表，**绝不静默丢词**
- 因为 `_词典` 只覆盖身体/发型/五官/衣着大类（场景、道具、年龄、武器一律翻不出来），`一致性.py` 自己补了一层 **`译补` 短语表**（约 60 条），在**中文原文上先做短语替换**再交给 `_译`

- `译描述细()` = `译描述()` + 额外报出「被 `译补` 救回来的词」
- `加译补({"中文": "english"})` 可以在运行期加词

### 7.1 踩过的坑（留给后续）

1. **中文模块名 `import 角色库` 在此环境会失败**。`一致性.py` 用 `_装模块(文件名, 别名)`：先 `__import__`，失败再退回 `importlib.util.spec_from_file_location` 按路径载入。实测成功。
2. **`清空()` 曾经出现「旧数据复活」**：`清空()` 内部调 `保存()`，而 `保存()` 内部调 `载入()`，一旦 `_已载` 缓存标志失效就会把磁盘上的旧库读回来，表现为「清空后 6 条数据又回来了」。**已修**：`清空()` 现在不再走 `保存()`，直接原子写盘，并在 `自测()` 开头加了一条「清空后磁盘必须真的为空」的自检。
3. **`编号()` 返回的条目必须带 `参考图` 键**（早期只有 `原图`，导致 `KeyError`）。
4. **`_译()` 会静默丢词**（只 print 报警）。必须把报警接住变成返回值，否则素材描述会悄悄少一截。
5. **相邻中文短语没有标点时会黏词**（`紫色杏眼` → `purplealmond-shaped`）。`_补译()` 用两侧垫空格 + 正则归一化解决。
