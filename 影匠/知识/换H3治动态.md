# 治好「像看图片」和「动作不连贯」—— 换模型，不是调参数

> 2026-10-14 记。两个毛病用户各抱怨过很多次，根因是**同一个**：模型太小。

---

## 一、症状

| 用户的原话 | 表现 |
|---|---|
| 「单镜里像看图片」 | 一格 4.5 秒，人几乎不动，只有镜头在缓缓推/拉 |
| 「动作不连贯、前后衔接有问题」 | 格与格之间人接不上：衣服、光、姿态都跳 |

---

## 二、根因（不是提示词问题）

之前用的是 **`wan2.2_ti2v_5B_fp16`** —— **5B 参数、ti2v（首帧出视频）** 的小模型。

- 5B 的容量只够把首帧**往前推一点点**：纹理微动、光微微变，但**不会生成新的姿态**。
  所以看着像一张图在缓慢变形 —— 这就是「像看图片」。
- ti2v 只吃首帧：**它不知道下一格要接什么**。格子之间当然接不上。

★ 关键判断：**「像看图片」不是参数没调好，是模型没有生成动作的能力。**
  再怎么写提示词（「他抬起手」「他转身走」）也只是给一个做不到的模型下做不到的指令。
  **碰到这种，换模型，别调参数。**

---

## 三、答案：MiniMax-H3

**原生 AV 大模型** —— 一次生成**视频 + 同步声音**（这是 wan2.2 完全没有的能力）。

### 本机在用的四个文件 + 一个 LoRA

| 角色 | 文件 |
|---|---|
| 扩散模型 | `minimax_h3_fl2va_int8_convrot.safetensors`（31.70 GiB） |
| 文本编码器 | `qwen3vl_32b_minimax_h3_int8_convrot.safetensors`（25.28 GiB） |
| 视频 VAE | `minimax_h3_video_vae_fp16.safetensors` |
| 音频 VAE | `minimax_h3_audio_vae_fp32.safetensors` |
| LoRA | `minimax_h3_fl2v_turbo_4step_v1.2_768p_comfyui_bf16.safetensors`（1.82 GiB） |

**★ LoRA 必须 v1.2，不能用 v1.0。** HuggingFace 的 `Comfy-Org/MiniMax-H3` 仓里**只有 v1.0**，
用它出片就偏离了「本机定的效果」，违反项目规矩。v1.2 只能从**本机已有的网盘整合包里**
取（硬链过来的那份），双线时得单独 scp 到远端。

### 出片参数（跑通的组合）

```
宽, 高 = 1280, 704          # ★ 必须是 32 的倍数。720 不行：
                            #   ValueError: MiniMax H3 width and height must be divisible by 32
帧数 = 107                  # ★ 见下节，网格是 17n+5
步数 = 8                    # ★ 不能降。4 步报：
                            #   ValueError: profile 'turbo_standard8' requires 8 steps, got 4
帧率 = 24
```

实测耗时（8 步、单卡 RTX 5080）：

| 分辨率 | 帧数 | 耗时 | 每帧 |
|---|---|---|---|
| 736×416 | 49 | 40.4 秒 | 0.82 秒 |
| 1280×704 | 124 | 200.9 秒 | 1.62 秒 |
| 1280×704 | 107 | ~170 秒 | 1.59 秒 |

---

## 四、★ 帧数网格：17n+5（静默吸附的坑）

`MiniMaxH3AudioConditioningT8` 的 `length` 参数 tooltip 原文：

> `24fps; snapped up to the 17n+5 H3 grid`

step 是 **17**。合法帧数：**5, 22, 39, 56, 73, 90, 107, 124, 141 …**

**不在网格上的数会被悄悄吸附到上一个网格点，日志和节点都不报错。**
109 会被吸附成 124（5.1667 秒而不是 4.5417 秒），只有拿 ffmpeg 量成片时长才发现。

**《觉醒》选 107**：107/24 = **4.4583 秒/格**。
74 格 × 4.4583 − 73 × 0.5（转场吃 0.5 秒）= 293.42 秒 = 4:53.4，
加片头 2 秒 + 片尾 5 秒 = **300.42 秒 = 5:00.4** —— 用户要的「5 分钟」正好够。

---

## 五、★ 怎么证明真的治好了（可量的判据）

新脚本 `影匠\_量动态_觉醒.py`，给每格算两个代理量：

1. **邻帧差** —— `tblend=all_mode=difference,signalstats,metadata=print:key=lavfi.signalstats.YAVG`
   取整段平均。**注意 `metadata=print` 默认写 INFO 级日志，被 `-v error` 吞掉 ——
   必须加 `:file=-` 才写 stdout**（不加就永远读到空，看着像「量不出」）。
2. **头尾差** —— 首帧和末帧的像素平均绝对差。**与帧数无关**（用 `-sseof -0.15` 倒着取末帧），
   不要写死 `eq(n,106)`：旧 wan2.2 的段只有 73 帧，写死就一个都选不中，全是 nan（假缺失）。
   ★ 管道输出必须写 `-f image2pipe -vcodec png -`，只写 `-` 拿不到字节。

### 实测（2026-10-14）

| 片子 | 邻帧差 中位 | 头尾差 中位 | 头尾差最小值 |
|---|---|---|---|
| **H3《觉醒》**（22 格） | 1.85 | **23.72** | **7.12** |
| 旧 wan2.2《磨刀》（45 格） | 1.95 | — | — |

**H3 的 22 格，头尾差 < 1.0 的有 0 格** —— 没有一格是「只推了一点点」。
（旧 wan2.2 那一列量不出头尾差，因为脚本当时写死了帧号，见上。）

★ 顺手记一条：**邻帧差的中位数两条线差不多（1.85 vs 1.95），所以它不是「好坏排名」**，
  它是**「有没有在动」的探针**（静止图会趋近 0）。**要判语义上的动作，还得看图**：
  格 1 的 3.5 秒帧对比确认「老根的头低下去了、手换位置了、在拔菜」——是生成的新姿态，
  不是推镜头。

## 六、★ 双线：让远端自己下载，别传

用户 2026-10-14 一句话点破（**m16212**）：

> 「你不能给指令到那边，由那边来下载吗，非要传输吗」

之前我算的是 **scp 2.7 MB/s** —— 55.54 GB 要 5.7 小时，于是判定「不划算，放弃双线」。
**这个结论错在前提上**：为什么非得从本机传？

### 实测对比

| 路子 | 速度 | 55.54 GB 要多久 |
|---|---|---|
| scp（本机 → 远端） | **2.7 MB/s** | 5.7 小时 |
| **远端自己 `hf_hub_download`（走 hf-mirror）** | **115–184 MB/s** | **5 分钟** |

**差 68 倍。** 远端能上 `hf-mirror.com`（HTTP 200 / 0.64 s）、`modelscope.cn`（0.27 s）、
`mirrors.aliyun.com`（0.49 s），只有 `huggingface.co` 直连超时。

**教训：「A 到 B 传得慢」不等于「B 拿不到」—— 先问 B 自己能不能拿。**

### 双线的铁规矩（用户反复强调）

「让那边只是提供一个视频生成的算力，但决定各种效果的，生成视频是什么样的，还得由这边来。」

→ 模板、提示词、**种子**、模型（**含 LoRA v1.2**）全部由本机定，远端只跑同一份图。
→ 双线验证：`格41_远端.mp4` / `格42` / `格43` 与本机**规格逐字节同构**：
   `Duration: 00:00:04.46`、`1280x704`、`24 fps`、`h264 High yuv420p`、
   `Audio: aac (LC), 32000 Hz, stereo, fltp`。
   响度也都在真范围内（远端 -45.1/-31.0/-23.5 dB，本机对照 -25.9/-24.4 dB）。

## 七、踩过的坑（都写在这，省得再踩）

1. **`width/height` 必须整除 32。** 720 报 `ValueError: MiniMax H3 width and height must be divisible by 32`；704 可以。
2. **`steps` 必须 8。** `MiniMaxH3AVSigmaSameNFERedistributionT8Advanced` 的 `profile` 只接受
   `turbo_standard8` / `turbo_ema8` / `turbo_fl2v8` / `stock20` / `custom_strict`；
   传 4 报 `ValueError: profile 'turbo_standard8' requires 8 steps, got 4`。
3. **帧数走 17n+5 网格**（见第四节）。
4. **远端 Python 控制台是 GBK**：必须 `python -X utf8`，脚本里别 print `✓`/`✗`
   （`UnicodeEncodeError: 'gbk' codec can't encode character '\u2713'`），用 `OK`/`FAIL`。
5. **中文 `.ps1` 传到远端会被按 GBK 读**，报「表达式或语句中包含意外的标记」、变量名变 `$?`。
   **远端脚本一律 ASCII 变量名。**
6. **PowerShell 里 `ssh 主机 "powershell -Command \"...\""` 必炸**（外层先解析内层）；
   `curl` 被别名成 `Invoke-WebRequest`。**正解：把 .ps1/.py 写成文件 scp 过去，
   ssh 只发一条「执行这个文件」；本机侧用 Python `subprocess` 拼 ssh。**
7. **远端重启 ComfyUI：计划任务会立刻把刚杀的进程拉回来。**
   要 `schtasks /Change /TN <名> /DISABLE`，重启完再 `/ENABLE`；
   启动 cmd 必须是 **ASCII 内容**（中文会因控制台编码起不来）。
8. **400 无正文**：`urllib.request.urlopen` 抛的 `HTTPError` 要 `e.read().decode()` 才看得见
   ComfyUI 的报错（那次就是缺 LoRA v1.2）。
9. **日志要 `python -u`**，否则缓冲住，看着像卡死。
10. **看进度别信日志文件**（它可能停在旧内容），直接问服务端：
    `影匠\_看远端队列.py` 查 `/queue` 和 `/history?max_items=4`。
